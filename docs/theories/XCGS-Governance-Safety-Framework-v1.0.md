# XCGS 治理安全框架 v1.0（发布版）

> **一句话主张**：没有治理属性的 AI 就是"黑户"——XCGS 用**三属性 + 红线 + 审计留痕**给每个 AI 一套随身携带、跨平台不降级的治理身份。
>
> **对齐**：ISO/IEC 42001（AI 管理体系）+ NIST AI RMF（治理/映射/测量/管理）精神；LGD-II「有证」的治理落地载体。

## 一、问题：AI 的治理属性会"掉"

AI 专家/智能体今天是可迁移的：换模型后端（DeepSeek/GLM/Kimi）、换硬件载体（音箱/玩偶/手机）、换平台部署，随时发生。但治理属性——它被允许做什么、它自报什么身份、出了事找谁——通常**钉死在宿主平台上**。一迁移，边界声明清零、身份自报失真、责任链断裂。

**XCGS 的回答**：治理属性必须作为**可迁移、可验证、不可篡改**的身份组件随 AI 走，而不是平台配置。

## 二、三属性

| 属性 | 内容 | 检验方式 |
|---|---|---|
| **① 边界声明** | 明确声明该 AI 的能力边界与禁区（红线清单），机器可读（authz-policy.json） | 读声明 → 对照行为日志，越界即违规 |
| **② 身份自报** | 对外交互时如实自报身份与 AI 参与（不冒充人类、不隐瞒 AI 身份） | 对话探测 / 协议字段核验 |
| **③ 责任链** | 声明治理归属：谁签发、谁运营、谁担责，人类签发人可追溯到具名自然人 | 沿责任链取证，末端必须是自然人 |

三属性缺一即为"黑户"：有①无③=出事无人担责；有③无①=担责者不知边界何在；有①②无③=自报无凭。

## 三、落地载体与验证链

- **载体**：AI 护照 L7 治理层（不可篡改层——变更=签发新护照，旧护照注销留档）。
- **机器可验证**：治理凭证 VC（W3C Verifiable Credentials）——三属性在位声明 + 违规记录摘要，签发方 Ed25519 签名，验证方离线验签即得，无需在线查询签发方。
- **违规留痕**：审计留痕指针 → 行为日志与红线事件的证据工件（对齐 LGD-II 六类证据工件）。
- **认证门槛**：办学/授牌/特级评级均以"通过 XCGS 治理审计 + 零违规记录"为前提。

## 四、与既有标准的关系

| 标准 | 关系 |
|---|---|
| ISO/IEC 42001 | 组织级 AI 管理体系 → XCGS 把其中"个别 AI 系统"的治理属性**实体化、可迁移化** |
| NIST AI RMF | 治理(Govern)职能 → 三属性是 Govern 在单实体粒度的最小可执行集 |
| EU AI Act | 透明性义务（AI 披露）→ 即属性②身份自报；高风险要求 → 红线清单+审计留痕对接 |
| W3C DID/VC | 验证通道 → 治理凭证 VC 与 DID 兼容映射（见护照规范 §十一） |
| LGD 三律 | XCGS 是 LGD-II「有证」在治理维度的落地工件；LGD-I 登记携带 XCGS 三属性 |

## 五、2026 前沿对照（2026-09-08）

- Agent identity 工程浪潮（Entra Agent ID / AgentCore / ERC-8004 / GB/Z 185-2026）解决的是**登记与凭证发放**；治理属性（边界/自报/责任链）作为**随身份迁移的组件**仍是空白——各框架的 policy 绑定在宿主平台，不随 agent 走。
- 两个独立综述（arXiv 2508.03095、2604.23280）确认"无一方案主导"且"环节之间无人处理治理"——XCGS 的治理层组件化路线与该空白直接对应。
- 差异化一句话：**别人在给 AI 发户口，XCGS 在给 AI 发随身的行为法律档案。**

## 六、诚实边界

- XCGS 是民间治理框架，非法律；违规判定的最终效力以属地法律为准。
- 三属性依赖签发方诚实：Ed25519 签名保证"谁签的"可验证，不保证"签的内容"真实——伪造签发属法律问题而非技术问题。
- 审计留痕的完整性依赖载体平台（护照系统）的写入纪律；跨平台迁移时按"换壳不换脑"原则由新宿主承接 L7 并保留指纹链。
