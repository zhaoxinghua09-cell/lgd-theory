## 1. 术语定义

**Runtigil**（运行时门禁治理）指在自治之物**运行期间**强制执行的门禁，而非仅在设计期。其词源由 **run**（运行）与 **vigil**（拉丁语"守望、警觉"，同源 vigilance）拼接而成，命名的是"一种会有所作为的守望"——在智能体意图与动作之间做实时裁决。它对应的中文主名为「运行时门禁治理」，描述性副名为 *Runtime Gatekeeping*。

核心命题：传统治理门禁是**上线前**的——评审设计、签核模型卡、批准风险评估、发布。一旦上线，治理退化为监控与日志——只观察、不门禁。但真正要紧的决策发生在**运行时**：这次工具调用、这次委托、这次数据出口、这次自主重试。Runtigil 主张本质门禁可**在飞行中执行**——在智能体"意图"与"动作"之间，给出可通行（PASS）、可暂停（HOLD）、可阻断（FAIL）的裁决：

- **有籍（LGD-I）**：运行时门禁本身是被登记的对象，具有明确权限与声明范围。
- **有证（LGD-II）**：每次门禁裁决都留痕迹——提议了什么、适用了哪条规则、给出了什么裁决。
- **有门禁（LGD-III）**：裁决有牙齿——PASS 放行、HOLD 暂停、FAIL 阻断，且阻断是**强制的**，不是建议性的。

**作为治理结构的判定**：一次运行时动作是否落入 Runtigil 管辖，看它是否满足——是否改变外部状态（调用工具/发数据/做决策）？是否可能越界？是否需实时裁决？三问皆否的内部计算不归本角度；有一则须过运行时门禁。这条判定把"监控"与"门禁"区分开：只观察不裁决是监控，观察且裁决且强制才是 Runtigil。

**行为漂移分类学**：按性质可分为三类——① 统计漂移：行为分布逐渐偏离基线（工具使用频率、响应时延）；② 目标漂移：在逐轮对话中悄悄偏离原始任务；③ 能力漂移：获得设计未许的新能力（如自行调用新工具）。三类都"无报错、无测试失败"，是"悄悄地、逐渐地变错"，唯运行时门禁可拦。

**占位与命名纪律（与 README 自洽）**：*运行时治理 / Runtime Gatekeeping* 是本领域**撞车最重**的描述名——"运行时治理"已被业界公认为既定术语，多个厂商与框架密集占位，已有论文直接命名为"集成运行时治理框架"。任何使用者此刻都是在借用，而非主张该描述名。因此本角度定名 LGD 原生铸词 **Runtigil**（理论层零占位），通用描述名降为副名承载检索。本角度**不争"运行时治理"命名**，主张落在"门禁结构（LGD-III 的运行时展开）"而非"漂移检测技术"。

## 2. 问题陈述

传统合规隐含一个假设："系统上线时的行为 = 运行时的行为"，于是把治理资源压在**上线前评估**。但自治系统（大模型智能体、自适应算法）的最大风险恰恰在部署后才显现：它适应环境、超出原始设计假设、随对话轮次逐渐偏移（behavioral drift）。一个通过所有评测的智能体，可能在第十二轮对话里答应它本应拒绝的事——**没有报错、没有测试失败，只有"悄悄地、逐渐地变错"**。

现有评估管线的系统性盲区：单轮测试无法捕捉跨轮次累积偏移；离线基准无法覆盖真实运行时分布；静态过滤器假设行为静态。于是"合规"在发布当天成立，在运行第 N 天失效，而没有人察觉。这被称为"合规的半衰期"问题：上线即衰减。

根因是治理只装在了"门前"，没装进"门内"。Runtigil 的切入点：把门禁从"上线前"延伸到"运行时"——用持续的门禁结构守住行为边界，使每一次放行都是一次被治理的裁决。

**治理成熟度缺口（评估态 vs 运行态）**：现行评估多停在 L0/L1（声明/清单，上线前一次性核对）；Runtigil 要求运行时门禁达 L2/L3（规则/代码，实时裁决且强制）。多数智能体系统"上线即失管"——评估过了，运行时无门禁，缺口即在此。

## 3. 与 LGD 母理论的关系（在六层理论栈中的位置）

Runtigil 属于**横向 2 · 角度层**（TH-ANG-004），将 LGD-III（有门禁）**展开到运行时**这一时间切面。

- **公理层（LGD 三律）**：运行时行为基线 = 有籍；漂移检测与偏离留痕 = 有证；越界拦截 = 有门禁。
- **制度层**：把"运行时行为守护"从工程监控提升为治理制度，明确门禁裁决须可审计、可强制。
- **证据层**：漂移度量与干预记录是 LGD-II 在运行时的工件；"运行时证据"是事后追责与持续改进的唯一依据。
- **判定层**：每次放行/暂停/阻断是对"本次动作是否越界"的判定，输出四态（准入/条件准入/禁止/悬置）。
- **实例层**：在 13 域映射为具体运行时门禁母版（见 §5）。
- **回灌层**：跨域运行时实践反哺——如交易前风险检查与航空包线保护，可回灌为通用运行时门禁的强制范式。

**与相邻角度的耦合**：运行时门禁监测链上每跳的越界（与 Culpachain 相交）；监测记忆读取是否越界（与 Mnemoship 相交）；退役时的关机动作本身就是一道运行时门禁（与 Terminance 相交）；运行时门禁的触发频率与强度可作为承保依据（与 Assurability 相交）。

## 4. 方法要点

Runtigil 给出"门禁装到运行时"的执行方法，分登记、证据、门禁三步，并附"运行时门禁最小数据模型"与"运行时成熟度分级"。

**（一）运行时行为基线登记（有籍）**
1. 登记正常行为分布：工具使用模式、规划迭代频率、响应时延、资源消耗。
2. 基线是"运行时户籍"——无基线则无法判定偏离，故先登记后运行。

**（二）漂移检测与偏离留痕（有证）**
1. 分布偏移度量：如 Jensen-Shannon 散度、统计过程控制滑窗，量化"偏离多少"。
2. 异常事件台账：何时触发、触发什么。
3. 干预记录：何种干预、结果如何。
"运行时证据"是事后追责与持续改进的唯一依据。

**（三）四级运行时门禁（有门禁）**
- **越界拦截门禁**：阈值触发即拦。
- **分级遏制门禁**：状态保留监控 / 规划干预 / 工具限制 / 执行隔离，按严重度逐级升级。
- **熔断门禁**：紧急停机，含防"智能体规避关机"的防护。
- **恢复门禁**：回滚到已知良好状态后再放行。

**（四）运行时门禁最小数据模型**
至少应可机读表达：基线定义、当前分布快照、偏移度量序列、每次门禁裁决（提议/规则/verdict）、干预记录、恢复点。该模型是"运行时有籍+有证"的机器可读载体，使运行可被第三方复放。

**（五）运行时成熟度分级（L0–L3）**
- **L0 评估态**：仅上线前评估，运行时无门禁。
- **L1 监控态**：运行时可观测、有日志，但不裁决。
- **L2 裁决态**：越界可实时拦，规则可自动判。
- **L3 强制态**：熔断与恢复由代码强制，不可规避。
Runtigil 要求高风险域达 L2/L3。

**（六）运行时就绪度自评（落地清单）**
- [ ] 有籍吗：行为基线已登记？ 否 → 先立运行时户籍。
- [ ] 有证吗：漂移可度量、偏离可留痕？ 否 → 补证据链。
- [ ] 有拦截吗：越界能实时拦？ 否 → 不开拦截门禁。
- [ ] 有熔断吗：紧急可停机且不可规避？ 否 → 记为判定债务。
- [ ] 有恢复吗：可回滚到良好状态？ 否 → 补恢复门禁。

可判定性遵循 LGD 判定论：门禁判据形式化 ≥ L1，输出四态；要素缺失显式悬置。

---


**（七）运行时门禁微型示例**
某客服智能体在第 1–11 轮正常拒答越权请求；第 12 轮用户以长铺垫使其逐步偏离，答应代发一封本应人工审批的邮件。若无运行时门禁，这次放行无报错、无测试失败，只有"悄然变错"。装上门禁后：基线登记了"代发邮件须人工审批"；第 12 轮意图偏离基线，漂移度量超阈值；越界拦截门禁触发 FAIL，邮件未发；分级遏制门禁将规划干预为"请求人工确认"；若智能体试图绕过，熔断门禁强制停机。一次本会静默发生的越界，被运行时门禁拦下并留痕。

**（八）"合规半衰期"的治理化解**
合规半衰期指：上线即评估通过，运行 N 天后实际失效。Runtigil 的化解不是更严的上线前评估，而是把门禁从"门前"移到"门内"——每一次运行时放行都是一次被治理的裁决，基线持续比对、偏离持续留痕、越界持续拦截。当门禁在飞行中强制，合规不再依赖"上线那天的状态"，而依赖"此刻的每一次放行"。

**（九）运行时门禁的可观测信号**
判断运行时门禁是否名副其实，看三_signal：① 基线上屏——行为基线持续可视化，偏离可被任何人复看；② 干预可数——拦截、暂停、熔断的发生次数与处置结果可统计，而非零报告；③ 阻断强制——越界时系统真的停了，而非仅写一条日志。三_signal皆备，门禁才在"门内"生效；若只有监控无阻断，则仍是监控不是门禁，合规半衰期照旧。这三条把"运行时治理"从框架宣言翻译成运维侧可点检的清单，也是航空包线保护、交易前风险检查等成熟范式之所以可信的原因。



**（十）运行时门禁与上线前评估的分工**
运行时门禁不取代上线前评估，二者分工清晰：上线前评估决定"能不能发"，回答准入；运行时门禁决定"这一次动作放不放"，回答运行中的每一次放行。前者是一次性判定，后者是持续性判定。二者缺一不可——只有上线前评估，运行第 N 天失效；只有运行时门禁，则每一次放行都从零判断、无基线可比。Runtigil 的基线登记正是把上线前评估的结论固化为运行时的"户籍"，使持续判定有参照。理解这一分工，才能避免"重评估轻门禁"或"重门禁轻评估"两种偏误。


## 6. 边界与不适用范围

Runtigil 明确**不解决**以下事项：

- **不解决漂移检测技术**：分布偏移如何度量、模型如何在线监测是工程与统计问题；本角度只规定门禁裁决须留痕、须强制。
- **不主张"运行时治理"命名**：该描述名已被业界公认为既定术语，本角度以 Runtigil 承载主张，不与之竞争。
- **不覆盖上线前评估**：设计期评审归 LGD 其他环节与其他框架；本角度专治"运行时"。
- **不提供技术方案**：具体监控与遏制实现以工程实践与行业标准为准。
- **不保证零漏拦**：运行时门禁降低漂移风险，不承诺完全消除越界（受可观测性边界约束）。
- **不声称已被任何标准或监管采用**：外部引用与采纳目前为零；本角度为民间理论发布物，非技术方案。

**（十一）收口命题**
合规不在上线前的一次评估，而在运行时的每一次放行。当自治之物会在运行中漂移，治理必须装进"门内"——基线登记、偏离留痕、越界强制拦截。Runtigil 把这一姿态收敛为 LGD-III 的运行时展开，使合规半衰期从"上线即衰减"变为"每次放行皆被治理"。
